## Инварианты
1. Задача и проект имеют одинаковый tenant_id.
   Защищено схемой: составной FK `tasks(tenant_id, project_id) → projects(tenant_id, id)`.
   Доказательство (негативная проверка, вставка задачи Alpha в проект Beta):
   ```
   ERROR:  insert or update on table "tasks" violates foreign key constraint "tasks_tenant_id_project_id_fkey"
   DETAIL:  Key (tenant_id, project_id)=(10000000-0000-0000-0000-000000000001, 22000000-0000-0000-0000-000000000002) is not present in table "projects".
   ```
2. Проект существует до создания задачи — тот же составной FK (у проекта есть PK `(tenant_id, id)`).
3. Идентификатор задачи уникален внутри арендатора: PRIMARY KEY (tenant_id, id) — схема.

## EXPLAIN (ANALYZE, BUFFERS) «горячего» запроса (набор 120k)
```
 Limit  (cost=0.42..45.37 rows=50 width=41) (actual time=0.034..0.042 rows=50 loops=1)
   Buffers: shared hit=5
   ->  Index Scan using tasks_open_by_project on tasks  (cost=0.42..6082.77 rows=6765 width=41) (actual time=0.033..0.039 rows=50 loops=1)

         Buffers: shared hit=5

```

Подтверждает ли план предполагаемую причину роста p99 при увеличении workers?
План горячего запроса на наборе 120 000 строк остался тем же Index Scan без Sort (50 строк,
shared hit=5, read=0, Execution Time 0.068 ms — как и 0.066 ms на базовом наборе 20 000).
Сам запрос не подорожал: страницы горячего проекта целиком лежат в кеше, дисковых чтений нет.
Значит, рост p50/p95/p99 при workers=32 (p99 ≈ 3.0–3.3 мс против ≈ 1.0–1.4 мс при workers=1/8)
вызван не планом и не диском, а насыщением процессора: 32 бэкенда PostgreSQL (процесс на
соединение) + 32 горутины клиента конкурируют за 20 логических ядер хоста, на которых ещё
работают ~30 посторонних контейнеров. В замкнутой системе это классическое поведение: время
пребывания растёт из-за очереди на обслуживание, а не из-за самого обслуживания.

Растёт ли пропускная способность пропорционально числу горутин?
Нет. workers 1 → 8: ~2 300 → ~13 900 op/s (×6.0 при ×8 горутин — почти линейно, малый дефицит
из-за фиксированных издержек короткого опыта). workers 8 → 32: ~13 900 → ~23 400 op/s
(×1.7 при ×4 горутин — далеко не пропорционально). Ограничивающий ресурс по данным опытов —
CPU: (1) план и кеш не изменились (hit=5, read=0 — диск не задействован);
(2) pool = workers, очередь на соединение не образуется — пул не является бутылочным горлышком
в этих опытах; (3) при этом среднее время ответа выросло с ~0.54 мс до ~1.32 мс — при
неизменной стоимости обслуживания растёт ожидание, что и происходит при исчерпании процессора.
Утилизация CPU непосредственно не логгировалась — вывод опирает на план, буферы и рост задержек.

## Вывод
Что ограничивает опыт и почему этих данных пока недостаточно для решения о шардинге?

Ближе всего к исчерпанию процессор: масштабирование workers 8 → 32 даёт лишь ×1.7 роста пропускной способности и
утраивает хвост (p99 ~3 мс), при неизменном плане и полностью прогретом кеше. Замер
оптимистичен: прогретый кеш (hit=5, read=0), «удобное» распределение (80/20 с крошечным
горячим набором из 50 строк), замкнутый цикл генератора (сам себя притормаживает и
недооценивает хвост при перегрузке), короткое окно в 500 запросов, локальный transport.

Для решения о шардинге не хватает: измерений при открытом потоке независимых клиентов,
длительных окон наблюдения, смешанной нагрузки с записью, объёмов, при которых рабочий набор
перестаёт умещаться в память (миллионы строк), мониторинга насыщения (утилизация CPU, iostat,
pg_stat_statements) и повторения на изолированной машине без посторонних контейнеров.
Сейчас ни один ресурс не измерен исчерпанным — оснований для разделения данных нет.
