# РХД-03. Демон перекоса записи (write skew) на READ COMMITTED

Опыт обязательной части: две транзакции READ COMMITTED в двух независимых
psql-сессиях под рабочей ролью `teamboard_app` (RLS включена, арендатор
привязывается транзакционным `set_config('app.tenant_id', ..., true)`).

## Инвариант предметной области

Задачи `a1900000-0000-0000-0000-000000000001` ("Existing one") и
`a1900000-0000-0000-0000-000000000002` ("Existing two") проекта
`Concurrency demo` — дежурная пара: завершить свою задачу разрешено,
только если партнёр ещё `open`. Одновременно `done` быть нельзя.

Обе транзакции пишут **разные** строки, поэтому конфликта блокировок строк
нет: решение принимается по отсутствующему в снимке изменению партнёра.
Это и есть перекос записи — `SELECT ... FOR UPDATE` по прочитанным строкам
здесь не помог бы, блокировать нечего: сами строки партнёра в момент
решения не менялись.

## Расписание

* Сессия A: `BEGIN ISOLATION LEVEL READ COMMITTED` → чтение статуса
  партнёра (…0002) → `pg_sleep(3)` (окно для симметричного чтения B) →
  `UPDATE` своей задачи (…0001) в `done` → `COMMIT`.
* Сессия B (стартует сразу после A, укладывается в окно сна A):
  `BEGIN ISOLATION LEVEL READ COMMITTED` → чтение статуса партнёра
  (…0001) → `UPDATE` своей задачи (…0002) в `done` → `COMMIT`.

Скрипты: `demo_write_skew_session_a.sql`, `demo_write_skew_session_b.sql`.

## Итог

`both_done = t`: обе транзакции честно проверили предусловие в своём
снимке (у каждой партнёр был `open`), обе выполнили `UPDATE 1`, обе
успешно зафиксировались — итоговое состояние противоречит предпосылке
«не обе задачи done одновременно». На READ COMMITTED каждая команда
корректна по отдельности, а вместе они нарушают правило предметной
области; блокировать нечего, т.к. каждая меняет свою строку.

Закрывается аномалия уровнем SERIALIZABLE + повтор транзакции целиком:
демонстрация — в тесте `TestSerializableClosesWriteSkew`
(`internal/command/race_test.go`), где при том же барьере одна из
транзакций получает SQLSTATE 40001 и после повтора видит актуальный
счётчик.

Решение об адаптации: в методичке демон строится на таблице статусов
задач; здесь он адаптирован на выделенные demo-задачи арендатора Alpha
из миграции `004_idempotency.sql`. Основной датасет варианта А
(Alpha 100 000 / Beta 10 000 задач) опытом не затрагивается; после
опыта demo-задачи возвращаются в `open` пересборкой миграции 004.
