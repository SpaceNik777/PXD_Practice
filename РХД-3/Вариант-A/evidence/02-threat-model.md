# Модель угроз: внешний ключ без tenant_id (РХД-02, вариант А)

## Гипотетический сценарий

Пусть внешний ключ таблицы `project_members` ссылался бы на проекты только по
`project_id`:

```sql
-- ГИПОТЕТИЧЕСКИ, так НЕ сделано в этом проекте:
FOREIGN KEY (project_id) REFERENCES projects (id)  -- нельзя: id не UNIQUE
```

В нашей схеме такая конструкция невозможна синтаксически: первичный ключ
`projects` — составной `(tenant_id, id)`, отдельный столбец `id` не является
уникальным, и PostgreSQL не позволит создать FK по неуникальному столбцу.
Но предположим, что схему перестроили так, что `projects.id` стал глобально
уникальным (например, `id` объявлен первичным ключом, а `tenant_id` остался
обычным столбцом). Тогда FK только по `project_id` стал бы допустимым — и
появилась бы новая классовая уязвимость.

## Что стало бы возможным

Строка `project_members(tenant_id = Alpha, project_id = <проект Beta>, ...)`
проходила бы проверку ссылочной целостности: указанный `project_id` реально
существует в `projects` — просто там он принадлежит Beta. Последней линией
защиты осталось бы только правило RLS `project_members_isolation`:

- `WITH CHECK (tenant_id = app.current_tenant_id())` проверяет лишь то, что
  вставляемый `tenant_id` равен контексту (Alpha). Само пересечение
  «строка Alpha ссылается на проект Beta» RLS по одной таблице
  `project_members` не видит: предикат вычисляется по текущей строке и
  не делает подзапросов (это осознанное решение — см. раздел 2.6 методички).
- Итог: «участник арендатора Alpha в проекте Beta» успешно записалась бы,
  если RLS включён и контекст установлен, но запись ПОПАСТЁТ в таблицу,
  как только отключён, ошибочен или обойдён RLS (суперпользователь,
  `BYPASSRLS`, миграция, выполняемая владельцем без `FORCE`, ошибка в
  политике при рефакторинге).

## Почему составной FK — независимый уровень защиты

Составной ключ

```sql
FOREIGN KEY (tenant_id, project_id) REFERENCES projects (tenant_id, id)
```

требует существования пары `(tenant_id, project_id)` целиком. Пары
«Alpha, проект Beta» в `projects` нет, поэтому такая строка отклоняется
самим ядром ссылочной целостности, даже если:

- RLS выключен (`ALTER TABLE ... DISABLE ROW LEVEL SECURITY`);
- политика ошибочно удалена или ослаблена при рефакторинге;
- подключение выполнено под суперпользователем или ролью с `BYPASSRLS`;
- приложение вообще не устанавливает контекст арендатора.

Это эшелонированная защита: ссылочная целостность PostgreSQL не зависит от
правил RLS и прав роли, а проверки FK выполняются ядром, минуя RLS
(документация PostgreSQL: referential integrity checks bypass row security).
Фактический текст ошибки в тесте `TestTenantCannotAddMemberToForeignProject`
подтверждает, какой уровень сработал:

```
ERROR: insert or update on table "project_members" violates foreign key
constraint "project_members_tenant_id_project_id_fkey" (SQLSTATE 23503)
```

(а не `new row violates row-level security policy`): RLS `WITH CHECK` строку
с `tenant_id = Alpha` пропустил, потому что контекст тоже Alpha, — отклонил
её именно составной FK. Для сравнения, попытка записать строку с чужим
`tenant_id` (например, задачу Beta из транзакции Alpha) отклоняется раньше и
именно RLS: `new row violates row-level security policy for table "tasks"`.

## Сводка уровней для project_members

| Уровень | Механизм | Что предотвращает |
|---|---|---|
| 1. Граница приложения | `WithTenantTx(ctx, tenantID uuid.UUID, ...)` | Контекст арендатора не восстанавливается «по памяти»; uuid-тип исключает мусор |
| 2. Интерфейс репозитория | `ListProjectMembers(ctx, tenantID, projectID)` | Арендатор — обязательный явный аргумент |
| 3. Схема данных | PK `(tenant_id, project_id, user_id)` + составной FK `(tenant_id, project_id) → projects` | Строку «свой арендатор, чужой проект» отклоняет ядро даже при полностью неработающем RLS |
| 4. Роль и RLS | `teamboard_app` NOBYPASSRLS; политика `USING`/`WITH CHECK` по `tenant_id` | Чтение чужих строк и запись с чужим `tenant_id` при любой ошибке в тексте запроса |

## Остаточные риски (что RLS не закрывает)

- суперпользователь и роли с `BYPASSRLS` обходят правила безусловно;
- внутри одного арендатора RLS не разграничивает права пользователей
  (уровень «этот viewer не должен видеть этот проект» — задача сервисного
  слоя или отдельной модели прав);
- побочные каналы: сообщения о нарушении уникальности, метрики и планы
  запросов, размеченные идентификатором арендатора, выдают факт существования
  строк;
- структура таблиц и имена столбцов остаются видимыми.
