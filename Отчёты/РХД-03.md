## 1. Введение

### 1.1. MVCC и снимки

PostgreSQL работает на многоверсионном управлении конкурентным доступом (MVCC): оператор записи никогда не изменяет кортеж на месте — он создаёт новую версию строки (`xmax`/`xmin`), а читатели получают согласованный **снимок** данных. На уровне READ COMMITTED снимок берётся **на каждый оператор**, поэтому две последовательные команды одной транзакции могут видеть разные состояния. На уровне REPEATABLE READ/SERIALIZABLE снимок берётся **один раз на транзакцию**, а SERIALIZABLE дополнительно строит граф зависимостей (SSI) и **откатывает** транзакцию ошибкой `SQLSTATE 40001` (serialization_failure), если её фиксация могла бы нарушить сериальный порядок выполнения. Отсюда ключевое следствие: SERIALIZABLE не «блокирует аномалию», а **отказывается фиксировать** её — а отказ можно обработать повтором транзакции целиком с нового снимка.

### 1.2. Перекос записи против потерянного обновления

- **Потерянное обновление** (lost update): две транзакции читают одну строку, обе пишут — одна перезаписывает результат другой. Заметно даже на READ COMMITTED, лечится легко: `SELECT ... FOR UPDATE`, один атомарный `UPDATE ... WHERE` или версия строки.
- **Перекос записи** (write skew): две транзакции читают **набор строк**, каждая изменяет **разные** строки, но предусловие (инвариант) сформулировано над всем набором: «две дежурные не могут одновременно уйти», «в проекте не должно остаться ноль открытых задач», «не обе задачи пары могут быть done». Каждая транзакция по отдельности консистентна, блокировать нечего (строки разные), READ COMMITTED их пропускает — и итог противоречит предусловию. Классическое лечение — SERIALIZABLE + повтор по 40001/40P01 либо явные блокировки предиката (`FOR UPDATE` чтений-условий), либо ограничение уровня схемы.

Почему блокировок недостаточно при человеческом факторе: блокировку нужно **не забыть поставить** на каждом пути кода и на **всех** читателях условия; при динамических предусловиях над несколькими строками правильная область блокировки нетривиальна, а разработчик, добавляющий новый запрос мимо протокола, молча открывает окно аномалии. SERIALIZABLE закрывает класс аномалий **системно** — ценой необходимости обрабатывать 40001 повтором.

### 1.3. Идемпотентность: ключ + сохранённый ответ, а не «ровно один раз»

При таймаутах сети и повторных отправках клиент (человек, шлюз, брокер) может прислать ту же команду дважды. Гарантию «exactly-once» на распределённой границе дать нельзя; реальный инструмент — **идемпотентность по ключу**: команда несёт ключ `(tenant_id, key)`, сервер ведёт журнал `command_requests`, первая обработка сохраняет **ответ** (`response_body`) и момент завершения (`completed_at`), повтор с тем же ключом и **тем же содержимым** возвращает сохранённый ответ без повторной мутации. Изменённое содержимое при том же ключе — конфликт (`SQLSTATE 23505`-семантика / типизированная ошибка), а не тихое игнорирование. Итемпотентность гарантирует «не более одной предметной мутации на ключ», но **не** гарантирует, что ответ ровно один раз дойдёт до клиента — это ограничение фиксируется явно.

### 1.4. Адаптация чисел под датасет варианта А

Датасет варианта А (Alpha 100 000 задач) не предназначен для демонстраций конкурентных аномалий — гонки в нём недетерминированы. Миграция 004 добавляет в тенант Alpha отдельный **демо-проект** `11990000-0000-0000-0000-000000000001` («Concurrency demo», лимит открытых задач 3) с двумя задачами `a1900000-0000-0000-0000-000000000001/0002`. Все демонстрации и тесты работают только внутри него (после каждого теста проект возвращается к ровно двум задачам), поэтому основной датасет не искажается: контрольный подсчёт Alpha после всех работ — **100 002** (100 000 сидовых + 2 демо), Beta — **10 000**. Проверки РХД-02 (`internal/tenantdb`) сохранены с адаптацией ожидаемого счётчика Alpha под 100 002.

### 4.2. Шаг 1.1 — миграция 004_idempotency.sql

Демо-проект (tenant Alpha, лимит открытых задач 3) и две задачи:

```sql
INSERT INTO projects (id, tenant_id, name, open_tasks_limit)
VALUES ('11990000-0000-0000-0000-000000000001', '10000000-0000-0000-0000-000000000001',
        'Concurrency demo', 3) ON CONFLICT (id) DO UPDATE SET open_tasks_limit = EXCLUDED.open_tasks_limit;
INSERT INTO tasks (id, tenant_id, project_id, title, status) VALUES
 ('a1900000-0000-0000-0000-000000000001', ..., 'Demo A', 'open'),
 ('a1900000-0000-0000-0000-000000000002', ..., 'Demo B', 'open')
ON CONFLICT (id) DO NOTHING;
```

Таблица журнала идемпотентности — по образцу методички:

```sql
CREATE TABLE IF NOT EXISTS command_requests (
    tenant_id      uuid NOT NULL REFERENCES tenants(id),
    key            text NOT NULL CHECK (length(key) BETWEEN 8 AND 200),
    command_type   text NOT NULL,
    request_hash   text NOT NULL,
    response_body  jsonb,
    created_at     timestamptz NOT NULL DEFAULT clock_timestamp(),
    completed_at   timestamptz,
    PRIMARY KEY (tenant_id, key),
    CHECK ((response_body IS NOT NULL) = (completed_at IS NOT NULL))
);
CREATE INDEX IF NOT EXISTS command_requests_retention ON command_requests (created_at);

ALTER TABLE command_requests ENABLE ROW LEVEL SECURITY;
ALTER TABLE command_requests FORCE ROW LEVEL SECURITY;
CREATE POLICY command_requests_isolation ON command_requests
    USING (tenant_id = app.current_tenant_id())
    WITH CHECK (tenant_id = app.current_tenant_id());

GRANT SELECT, INSERT, UPDATE ON command_requests TO teamboard_app;
```

Замечания методички учтены: политика содержит **и `USING`, и `WITH CHECK`** (без `WITH CHECK` INSERT/UPDATE своего арендатора падал бы с 42501), гранты минимальны (`SELECT, INSERT, UPDATE`, без `DELETE` — журнал не стирается приложением), PK `(tenant_id, key)` изолирует ключи арендаторов друг от друга. CHECK-инвариант `(response_body IS NOT NULL) = (completed_at IS NOT NULL)` не даёт записать ответ без времени завершения и наоборот.

**Фактический вывод применения** (файл `evidence/03-write-skew-demo.md`, раздел «миграция 004»): `CREATE TABLE / CREATE INDEX / ALTER TABLE ×2 / CREATE POLICY / GRANT` — применено от `postgres`; контроль после наката: `alpha_tasks = 100002, demo_tasks = 2`. Накат обёрнут в единый `BEGIN/COMMIT` (psql `-1`): транзакционность проверена фактически — первая редакция файла содержала лишний `DELETE FROM command_requests` **до** `CREATE TABLE`, psql остановился по `ON_ERROR_STOP` и не оставил частичных объектов; после исправления миграция применилась целиком. Повторный прогон того же файла корректно проходит в режиме поддержки (`IF NOT EXISTS` / `ON CONFLICT`, NOTICE skipping) — миграция реентерабельна.

### 4.3. Шаг 1.2 — демон перекоса записи (READ COMMITTED)

Сценарий (`evidence/demo_write_skew_session_a.sql`, `_b.sql`, протокол `evidence/03-write-skew-demo.md`): две psql-сессии `teamboard_app`, каждая открывает явную транзакцию и выставляет свой тенант:

```sql
BEGIN;
SELECT set_config('app.tenant_id', '10000000-0000-0000-0000-000000000001', true);  -- true = до конца транзакции
```

Инвариант демо-пары: **задачи Demo A и Demo B не могут быть одновременно `done`** (каждая сессия вправе завершить свою задачу, только пока задача партнёра ещё `open`). READ COMMITTED — снимок на оператор:

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | читает статус Demo B → `open` (предусловие выполнено) | |
| 2 | | (пауза ~5 c) |
| 3 | | читает статус Demo A → `open` (предусловие выполнено) |
| 4 | `UPDATE tasks SET status='done' WHERE id=…0001` → `UPDATE 1`; `COMMIT` | |
| 5 | | `UPDATE tasks SET status='done' WHERE id=…0002` → `UPDATE 1`; `COMMIT` |

Каждая транзакция в **своём** снимке видела партнёра `open`; строки обновляли разные → конфликтов блокировок нет. **Фактический итоговый контроль**:

```
 both_done | version_a | version_b
-----------+-----------+-----------
 t         |         2 |         2
```

Инвариант «не обе одновременно» **нарушен** (`both_done = t`) — аномалия перекоса записи воспроизведена. Основной датасет не пострадал: демо выполняется в отдельном демо-проекте миграции 004; после всех тестов обе задачи возвращены в исходное состояние (`open`, version 1), что подтверждено контрольным SELECT (`demo_tasks = 2`).

Замечание по инструментарию: в терминале cmd использовалась пауза `ping -n 6 127.0.0.1 >nul` (≈5 с) — встроенный `timeout /t` в этом окружении блокируется сообщением «Входные данные не могут быть перенаправлены».

### 4.4. Шаг 1.3 — tenantdb.WithTenantTxOptions

`WithTenantTx` стал обёрткой над новой функцией, принимающей `pgx.TxOptions` (общая логика: `BeginTx(ctx, opts)` → транзакционный `set_config('app.tenant_id', …, true)` → `fn(tx)` → `Commit`; откат в defer через `context.WithoutCancel`, чтобы отменённый контекст не помешал откату):

```go
func WithTenantTx(ctx context.Context, pool *pgxpool.Pool, tenantID string, fn TxFunc) error {
    return WithTenantTxOptions(ctx, pool, tenantID, pgx.TxOptions{}, fn) // READ COMMITTED
}
```

Все места РХД-02 сохраняют поведение; SERIALIZABLE-путь (`pgx.TxOptions{IsoLevel: pgx.Serializable}`) используется командами ниже и тестами.

### 4.5. Шаг 1.4 — internal/command: RunSerializable и CreateTask

`retry.go` — повтор **только** по 40001/40P01 (замечание методички: повтор по иным ошибкам маскирует баги), не более 5 попыток, экспоненциальная задержка с джиттером, с уважением к контексту:

```go
var ErrConflictClass = errors.New("transaction conflict class (SQLSTATE 40001/40P01)")

func RunSerializable(ctx context.Context, maxAttempts int, fn func(ctx context.Context) error) error {
    // задержка: база 10ms << attempt, джиттер до половины задержки
    for attempt := 0; attempt < maxAttempts; attempt++ {
        err := fn(ctx)
        if err == nil { return nil }
        var pgErr *pgconn.PgError
        if !errors.As(err, &pgErr) || (pgErr.Code != "40001" && pgErr.Code != "40P01") {
            return err // не конфликт сериализации — не повторяем
        }
        // backoff + джиттер + select { case <-ctx.Done(): ...; case <-timer.C: }
    }
    return fmt.Errorf("%w: serializable retry budget exhausted", ErrConflictClass)
}
```

`create_task.go` — идемпотентная команда создания задачи с журналом. Отпечаток `request_hash` (sha256) считается по существенному содержимому (`task_id`, `project_id`, `title`) **до** цикла попыток. Каждая попытка выполняется в SERIALIZABLE-транзакции арендаря:

```sql
-- 1) заявка ключа
INSERT INTO command_requests (tenant_id, key, command_type, request_hash)
VALUES ($1, $2, 'create_task', $3)
ON CONFLICT (tenant_id, key) DO NOTHING;          -- RowsAffected == 0 → ключ занят

-- 2a) победитель: предусловие (LEFT JOIN, чтобы не считать свой INSERT) и предметная работа
SELECT count(*) FILTER (WHERE t.id IS NOT NULL AND p2.status = 'open') ... FROM projects p
LEFT JOIN tasks t ON t.project_id = p.id AND t.id <> $taskId WHERE p.id = $projectId ...
INSERT INTO tasks (id, tenant_id, project_id, title, status) VALUES (...) RETURNING version;

-- 2b) ответ журнала — одним UPDATE (CHECK-инвариант: response_body и completed_at вместе)
UPDATE command_requests SET response_body = $3::jsonb, completed_at = clock_timestamp()
WHERE tenant_id = $1 AND key = $2;
```

При `RowsAffected == 0` (ключ уже заявлен) — вычитывание записи журнала: несовпадение `command_type`/`request_hash` → `ErrIdempotencyConflict`; иначе ожидание в цикле (25 мс, `select` по ctx и `time.After`), пока конкурент не проставит `response_body + completed_at`, и возврат сохранённого ответа. Ошибки — типизированные маркеры с обёртками через `%w` (`ErrConflictClass`, `ErrIdempotencyConflict`, `ErrOpenTaskLimit`).

**Фактическая проба журнала** (`evidence/demo_idempotency_probe.sql`, протокол `04-idempotency-probe.md`), выполнялась от `teamboard_app` в транзакции с `set_config`:

- повторная заявка ключа без `ON CONFLICT` → фактический текст ошибки уникальности (SQLSTATE **23505**):
  ```
  ERROR:  duplicate key value violates unique constraint "command_requests_pkey"
  DETAIL:  Key (tenant_id, key)=(10000000-0000-0000-0000-000000000001, demo-key-20261009-0001) already exists.
  ```
- та же заявка с `ON CONFLICT (tenant_id, key) DO NOTHING` → **`INSERT 0 0`** — «число задетых строк при повторе CreateTask» равно **0** (ни новой заявки, ни тем более новой задачи: предметный INSERT выполняется только победителем заявки).

### 4.6. Шаг 1.5 — барьерные тесты перекоса записи

`race_test.go`. Предусловие: в демо-проекте лимит открытых задач 3, исходно открыто 2. Обе горутины должны вставить по задаче; инвариант: суммарно открытых ≤ 3.

`TestReadCommittedAllowsWriteSkew` — контрольная ветка: тот же барьер, но транзакции READ COMMITTED (`WithTenantTx`). Барьер ставится **между** чтением условия и INSERT. **Фактический вывод — PASS**, лог: обе вставки прошли, `open = 4 > 3` — аномалия воспроизведена (тест PASS фиксирует именно её).

`TestSerializableClosesWriteSkew` — рабочая ветка: обе горутины в `RunSerializable` (SERIALIZABLE, ≤5 попыток); синхронизация — буферизованный канал `ready` (ёмкость 2) и `close(release)`, ошибки передаются в канал ёмкости 2 (без `t.Fatalf` из горутин). Барьер действует только в первой попытке (`firstAttempt`-флаг): обе читают «открыто 2 → можно» → обе вставляют → SSI фиксирует rw-конфликт. **Фактический вывод — PASS**:

```

```

### 4.8. Шаг 2.1–2.2 — вариант А: оптимистическая блокировка

`update_task.go` — `UpdateTaskTitle(ctx, pool, tenantID, taskID, expectedVersion, newTitle)`: **один оператор** в транзакции арендаря (`WithTenantTx`; READ COMMITTED достаточен и потому оставлен по умолчанию — атомарный `UPDATE` сам по себе не допускает потерянного обновления, что задокументировано здесь как осознанное решение):

```sql
UPDATE tasks SET title = $1, version = version + 1, updated_at = clock_timestamp()
WHERE tenant_id = $2 AND id = $3 AND version = $4
RETURNING version;
```

0 строк → `ErrVersionConflict` (в этой модели «версия не совпала» поглощает «не найдено»: строка с чужой/несуществующей версией для команды неразличимы по смыслу — оба случая означают «перечитай и решай заново»; отдельный `ErrNotFound` не вводился, поведение задокументировано в коде).

`variant_a_test.go`, `TestOptimisticVersionConflict` — детерминированные барьеры, без sleep: обе горутины в **своих** транзакциях читают задачу и версию V, сигнал `ready`, `close(release)` — затем обе вызывают `UpdateTaskTitle(..., V, ...)`. **Фактический вывод — PASS** (`0.07s`): `successes = 1`, `conflicts = 1` (второй — `errors.Is(err, ErrVersionConflict) == true`); контроль: `count = 1` (одна запись), версия ровно `V + 1`, `title` — победителя. Ровно один победитель, никаких потерянных обновлений.

### 4.9. Шаг 2.3 — идемпотентный CompleteTask

### 4.10. Шаг 2.4 — RLS во всех уровнях изоляции

## 5. Вывод

**Что доказано фактически:**

1. **SERIALIZABLE закрывает перекос записи и допускает прозрачный повтор.** На READ COMMITTED барьерный тест и psql-демон воспроизводят аномалию (демо-пары: `both_done = t`; лимит проекта: `open = 4 > 3`); на SERIALIZABLE SSI отклоняет одну из транзакций (`SQLSTATE 40001`), `RunSerializable` повторяет её с нового снимка (факт: 1 повтор, `open = 3`, `successes = 1`), предметное состояние остаётся непротиворечивым. Повтор ограничен классом 40001/40P01, бюджетом 5 попыток и экспоненциальной задержкой с джиттером.
2. **Журнал идемпотентности делает команду безопасной при дубликатах.** Конкурентный дубликат ключа → ровно одна предметная вставка (`tasks = 1`, `command_requests = 1`), оба вызова получают идентичный ответ; повторная заявка ключа не задевает строк (`INSERT 0 0`); попытка «протащить» другое тело под тем же ключом пресекается (`ErrIdempotencyConflict` через `errors.Is`, первопричина — уникальность PK `(tenant_id, key)`, фактически наблюдаемая как 23505). CHECK-инвариант журнала не допускает ответа без `completed_at` и наоборот.
3. **Оптимистическая версия — ровно один победитель.** Два читателя одной версии V, одновременная запись: один успех (версия V+1), второй — типизированный `ErrVersionConflict`; ни потерянных обновлений, ни блокировок ожидания (один атомарный `UPDATE … WHERE version=$`, READ COMMITTED достаточно).
4. **RLS сохраняется во всех уровнях изоляции.** В SERIALIZABLE-транзакции арендаря чужие строки не читаются (0), запись чужого тенанта отклоняется политикой (42501) — изоляция арендаторов не зависит от уровня изоляции транзакций.

**Ограничения (зафиксированы честно):**

- часть проверок остаётся **интеграционной**: демон перекоса и тесты требуют живого PostgreSQL 17 с данным датасетом (поведение SSI и RLS в юнит-тесте без БД не воспроизвести); прогоны чувствительны к разделению стенда между пакетами (`-p 1`);
- повтор по 40001/40P01 **не спасает** от неопределённых (не-временных) ошибок — они возвращаются вызывающему коду немедленно, а исчерпание бюджета превращается в `ErrConflictClass`-обёртку;
- идемпотентность гарантирует «не более одной мутации на ключ» и одинаковые ответы, но **не гарантирует ровно-один-раз доставку ответа клиенту** (сеть/таймаут на обратном пути остаётся за пределами БД);
- адаптация к датасету: демо-проект миграции 004 постоянно занимает 2 задачи Alpha (итог 100 002), а тесты tenantdb ожидают это число — при изменении демо-набора ожидания нужно синхронизировать.

**Состояние на финише цикла РХД:** стенд rhd3 (postgres 17.10-alpine, порт 55434) — `healthy`, запущен; репозиторий `РХД-3/Вариант-A` — один коммит `03751e5`; `go test -race ./... -count=1 -p 1` — PASS (command 2.380s, tenantdb 2.179s), gofmt/vet чистые.
