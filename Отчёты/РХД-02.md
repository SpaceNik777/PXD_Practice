## 1. Введение

Цель работы — превратить общую базу PostgreSQL в хранилище нескольких арендаторов с изоляцией, которую можно **проверить и доказать**. Ключевая идея: изоляция не должна опираться на внимательность одного разработчика — она вытекает из устройства системы: из типов, из подписей методов, из ключей таблиц и из правил доступа самой базы данных.

Опорные положения теории:

- **Модель pool (общие таблицы)**: все арендаторы делят одни таблицы, у каждой строки `tenant_id`. Сильная сторона — плотность размещения и простые общие миграции; цена — единственное забытое `WHERE tenant_id = ...` способно раскрыть данные чужого клиента, причём такой запрос «не падает» и в журналах не выглядит ошибкой. `TeamBoard` работает в модели pool.
- **Определение арендатора ≠ изоляция.** Определение отвечает «от имени какого арендатора выполняется запрос» (проверенный токен/удостоверение на границе HTTP); изоляция отвечает «какие данные запрос действительно способен прочитать или изменить». Наличие `tenant_id` в токене ничего не доказывает, пока каждый путь доступа этот признак применяет.
- **Четыре уровня защиты** (независимы; каждый может ошибиться, остальные продолжают работать): (1) граница HTTP связывает проверенного участника с идентификатором арендатора; (2) интерфейсы служб и репозиториев требуют арендатора явно, отдельным параметром; (3) схема данных и текст запроса ограничены арендатором (составные ключи и FK); (4) роль базы данных и правила RLS запрещают обход первых трёх уровней — они реализованы не в коде приложения, а в ядре СУБД.
- **Контекст арендатора — настраиваемый параметр** `app.tenant_id`, устанавливаемый `set_config(..., true)` **локально для транзакции**; единица работы — транзакция, а не соединение (иначе физическое соединение из пула унаследует чужой контекст, либо запрос уйдёт по соединению без контекста).
- **NULL-семантика запрета по умолчанию**: `current_setting('app.tenant_id', true)` без параметра даёт `NULL`, сравнение `tenant_id = NULL` неопределённо, строка не проходит правило — «ничего не видно» получается без единой дополнительной строки кода.
- Доказательство изоляции — **отрицательный интеграционный тест под той же ролью БД, которой пользуется приложение** (тест под суперпользователем не доказывает ничего).

### 4.1. Шаг 1: миграция 003_rls.sql

Текст — из методички: `DO`-блок с идемпотентным созданием роли `teamboard_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`; схема `app`; функция

```sql
CREATE OR REPLACE FUNCTION app.current_tenant_id()
RETURNS uuid LANGUAGE sql STABLE PARALLEL SAFE
AS $function$
    SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid
$function$;
```

(`current_setting(..., true)` даёт NULL вместо ошибки при незаданном параметре, `NULLIF(..., '')` превращает пустую строку в NULL — пустое значение не приводится к uuid); `REVOKE ALL ON SCHEMA public FROM PUBLIC` + `GRANT USAGE/EXECUTE/SELECT,INSERT,UPDATE,DELETE` роли; `ENABLE`+`FORCE ROW LEVEL SECURITY` на `tenants/projects/tasks`; три политики `FOR ALL TO teamboard_app` с явными `USING` и `WITH CHECK` (`id =`/`tenant_id = app.current_tenant_id()`). Применение от postgres:

```
BEGIN
DO
CREATE SCHEMA
CREATE FUNCTION
REVOKE
GRANT
GRANT
GRANT
ALTER TABLE        -- ×6: ENABLE+FORCE на три таблицы
CREATE POLICY      -- ×3
COMMIT
```

(предупреждения psql `there is already a transaction in progress` вызваны комбинацией `-1` с явными BEGIN/COMMIT файла; миграция зафиксирована). Решения: роль создаётся без BYPASSRLS и не владеет таблицами (разделение владельца и рабочей роли); `FORCE` подчиняет правилам и владельца; функция STABLE — планировщик вычисляет её один раз, полезно для индексов, начинающихся с `tenant_id`.

### 4.5. Шаг 5: граница транзакции на Go (internal/tenantdb/tenantdb.go)

`WithTenantTx` из методички: `BeginTx` → `defer`-откат через `context.WithTimeout(context.WithoutCancel(ctx), time.Second)` (освобождение ресурсов даже при отменённом контексте; после успешного Commit откат вернёт `ErrTxClosed` и игнорируется) → `SELECT set_config('app.tenant_id', $1, true)` параметром запроса → callback получает `pgx.Tx` (не пул — нельзя «случайно» уйти на другое соединение) → `Commit`. Аргумент `tenantID uuid.UUID` (не строка) — некорректное значение отклоняется на границе приложения. `go get github.com/google/uuid` → v1.6.0 в go.mod.

### 4.7. Вариант А, пункт 1: таблица project_members (003b_project_members.sql)

Ключевой фрагмент:

```sql
CREATE TABLE project_members (
    tenant_id  uuid NOT NULL,
    project_id uuid NOT NULL,
    user_id    uuid NOT NULL,
    role       text NOT NULL CHECK (role IN ('owner', 'editor', 'viewer')),
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    PRIMARY KEY (tenant_id, project_id, user_id),
    FOREIGN KEY (tenant_id, project_id) REFERENCES projects (tenant_id, id)  -- составной
);
ALTER TABLE project_members ENABLE ROW LEVEL SECURITY;
ALTER TABLE project_members FORCE ROW LEVEL SECURITY;
CREATE POLICY project_members_isolation ON project_members
    FOR ALL TO teamboard_app
    USING (tenant_id = app.current_tenant_id())
    WITH CHECK (tenant_id = app.current_tenant_id());
GRANT SELECT, INSERT, UPDATE, DELETE ON project_members TO teamboard_app;
```

Применение от postgres и контроль сида:

```

INSERT 0 3        -- Alpha Core: owner, editor, viewer
INSERT 0 2        -- Beta Core: owner, viewer
COMMIT

 10000000-0000-0000-0000-000000000001 | 11000000-0000-0000-0000-000000000001 | 10000000-0000-0000-0000-000000000102 | editor
 10000000-0000-0000-0000-000000000001 | 11000000-0000-0000-0000-000000000001 | 10000000-0000-0000-0000-000000000103 | viewer
```

### 4.8. Вариант А, пункт 2: ListProjectMembers

Метод размещён в том же пакете `internal/tenantdb` (файл `members.go`), а не в отдельном `internal/members`. Обоснование: метод обязан выполняться исключительно через ту же `WithTenantTx` над тем же пулом; отдельный пакет либо дублировал бы `Store`, либо открывал второй путь к базе мимо границы «одна транзакция — один арендатор». Единая точка входа упрощает аудит: любой код, работающий с данными арендатора, проходит через одну сигнатуру с обязательным `uuid.UUID`-аргументом. Тело метода — `WithTenantTx(ctx, tenantID, ...)` и внутри транзакции `SELECT tenant_id, project_id, user_id, role, created_at FROM project_members WHERE tenant_id=$1 AND project_id=$2 ORDER BY user_id`: даже при ошибке в тексте запроса политика RLS скрывает чужие строки.

- **Alpha не может добавить участника в проект Beta** (`TestTenantCannotAddMemberToForeignProject`): вставка строки `(tenant_id=Alpha, project_id=Beta-проект, editor)` из транзакции Alpha. Фактический текст ошибки:

  ```
  ERROR: insert or update on table "project_members" violates foreign key
  constraint "project_members_tenant_id_project_id_fkey" (SQLSTATE 23503)
  ```

  Сработал **составной FK (уровень 3, схема данных)**, а не RLS: `WITH CHECK (tenant_id = app.current_tenant_id())` строку пропустил — её `tenant_id` равен контексту (Alpha), — но пары `(Alpha, Beta-проект)` нет в `projects`, и ссылочную целостность это отклонилло. Контрольный контраст: строка с **чужим** `tenant_id` (задача Beta из транзакции Alpha, раздел 4.4) отклоняется раньше и именно RLS — `new row violates row-level security policy`. Два уровня защиты демонстрируют независимость: RLS ловит подмену `tenant_id`, составной FK — подмену `project_id` внутри «своего» `tenant_id`.
- **Контекст пуст после фиксации** (`TestMembersContextDoesNotLeakAfterCommit`, отдельный тест для members): после `ListProjectMembers` под Alpha прямой pool-запрос `SELECT count(*) FROM project_members` на том же соединении (MaxConns=1) возвращает 0.

### 4.10. Вариант А, пункт 4: модель угроз (evidence/02-threat-model.md)

Сохранена как `evidence/02-threat-model.md`. Суть: в нашей схеме FK только по `project_id` невозможен синтаксически — PK `projects` составной `(tenant_id, id)`, отдельный `id` не уникален. Гипотетически при глобально уникальном `projects.id` такой FK стал бы допустим, и строка «участник Alpha в проекте Beta» проходила бы ссылочную целостность (указанный `project_id` существует — у Beta); `WITH CHECK` по одной таблице этого пересечения не видит (предикат вычисляется только по текущей строке, без подзапросов). Последней линией осталось бы только RLS — и защита рушилась бы целиком при его выключении, ошибке в политике или обходе (суперпользователь, `BYPASSRLS`, миграции владельца). Составной FK закрывает этот класс ошибок на уровне ядра СУБД независимо от RLS — эшелонированная защита (в таблице модели — все 4 уровня для `project_members` с перечнем остаточных рисков).

**Ограничения RLS (что работа сознательно не закрывает).** RLS не проверяет подлинность и не решает, кто такой пользователь; не разграничивает права **внутри** одного арендатора (это задача сервисного слоя или отдельной модели прав — у ролей owner/editor/viewer одинаковая видимость строк); не защищает от суперпользователя, ролей с `BYPASSRLS`, прямого доступа к файлам данных и копий резервных копий; не скрывает структуру таблиц и имена столбцов; сам по себе не мешает побочным каналам — сообщения о нарушении уникальности и метрики, размеченные идентификатором арендатора, выдают факт существования строк. Роль `postgres` использовалась только для миграций и контрольных проверок владельца — приложение и тесты подключаются исключительно как `teamboard_app` (порт 55433, стенд `rhd2`).
