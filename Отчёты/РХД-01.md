## 1. Введение

Цель работы — не ускорять базу, а создать **измеримую исходную точку**: базовый замер, относительно которого в следующих работах можно доказать пользу или цену производных представлений, таблицы исходящих сообщений и разделения данных по узлам. Сначала учимся отвечать на вопрос «сколько сейчас?», и только потом получаем право спрашивать «как сделать быстрее?».

Ключевые понятия из теории, использованные в работе:

- **SLI** (Service Level Indicator) — фактически измеренная величина (например, p95 времени ответа);
- **SLO** (Service Level Objective) — допустимый диапазон SLI; утверждение «p95 < 150 ms» становится целью только вместе с окном наблюдения и описанием нагрузки;
- четыре показателя: пропускная способность (оп/с), время ответа (полное, включая чтение всех строк), доля ошибок, насыщение;
- **процентили** вместо среднего: p95 — граница, в которую укладываются ≥95% наблюдений; среднее скрывает хвост и не соответствует ничьему реальному опыту. В генераторе процентили считаются методом ближайшего ранга `index = ceil(p·n) − 1` по отсортированному массиву всех успешных наблюдений;
- соотношение «пропускная способность ≈ конкурентность / среднее время ответа» — использовано ниже для проверки измерений;
- ограничение методики: генератор работает по **замкнутому циклу** (следующий запрос — после завершения предыдущего), поэтому сам себя притормаживает при перегрузке и **недооценивает хвост** задержек относительно потока независимых пользователей;
- инварианты защищаются на трёх уровнях: ограничение в схеме (работает всегда) > проверка в транзакции > фоновая сверка. В этой работе первый инвариант защищён именно схемой — составным внешним ключом.

Учебный сценарий — система `TeamBoard`: арендаторы (организации), проекты, задачи. Основной интерактивный запрос — последние 50 открытых задач проекта; основная изменяющая операция — создание задачи (в этой работе нагрузка только читающая, запись появится в работе 3).

### 4.7. Вариант А, пункт 1: расширение набора данных

### 4.8. Вариант А, пункт 2: распределение 80/20

Выбор цели детерминирован **номером задания** (повторы опытов воспроизводят то же распределение; workers остаётся параметром):

```go
// pickTarget детерминированно выбирает цель по номеру задания: из каждых
// пяти операций четыре (i%5 < 4) приходятся на «горячий» проект targets[0],
// каждая пятая — циклически по прочим десяти проектам.
func pickTarget(i int) job {
	if i%5 < 4 {
		return targets[0]
	}
	others := targets[1:]
	return others[(i/5)%len(others)]
}
```

Producer отправляет `pickTarget(i)`. На 500 запросов: 400 (ровно 80%) → горячий проект, 100 → по 10 на каждый из 10 прочих (равномерно). Прогрев выполняет все 11 запросов на каждом соединении пула.

**Подтверждает ли план предполагаемую причину изменения p99 при росте workers?** План на наборе 120 000 строк остался тем же Index Scan по `tasks_open_by_project` без Sort: 50 строк, `shared hit=5, read=0`, Execution Time 0.068 мс — практически как 0.066 мс на базовом наборе 20 000. Шестькратный рост таблицы не подорожал запрос: горячий набор (50 строк одного проекта) целиком в кеше, дисковых чтений нет. Значит, рост p99 (с ~1.0–1.4 мс при workers=1/8 до ~3.0–3.3 мс при workers=32) вызван **не** планом и **не** диском, а конкуренцией за процессор: 32 бэкенда PostgreSQL (процесс на соединение) + 32 горутины клиента на 20 логических ядрах хоста с ~30 посторонними контейнерами. План, таким образом, **подтверждает причину косвенно**: стоимость самого обслуживания неизменна, выросло ожидание в очереди — классическое поведение замкнутой системы при насыщении CPU.

**Растёт ли пропускная способность пропорционально горутинам?** Нет:

- workers 1 → 8 (×8): ~2.3 → ~13.9 тыс. оп/с — ×6.0 (близко к линейному; дефицит из-за короткого опыта и фиксированных издержек);
- workers 8 → 32 (×4): ~13.9 → ~23.4 тыс. оп/с — только ×1.7, при этом среднее время ответа выросло с ~0.54 до ~1.32 мс.

**Какой ресурс ограничивает?** По измеренным данным — CPU, и вот обоснование: (1) диск исключён — `Buffers: shared hit=5, read=0` в обоих планах, рабочий набор полностью в shared buffers; (2) пул соединений исключён как узкое место этих опытов — `pool=workers`, свободных горутин, ждущих соединение, нет (32 соединения у 32 горутин; очередь на acquire не образуется); (3) остаётся процессор: при неизменной стоимости обслуживания (Execution Time 0.068 мс) время ответа растёт с ростом конкурентности — растёт именно ожидание, а время ожидания при неизменной стоимости обслуживания растёт при исчерпании обслуживающего ресурса. Прямая утилизация CPU в опыте не логгировалась — это честное ограничение вывода (утилизация CPU здесь не измерена, вывод опирается на план, буферы и задержки).

## 5. Вывод

**Что измерено и чем подтверждено.** Создан воспроизводимый стенд (postgres:17.10-alpine, healthcheck, том; порт 55432 из-за занятого 5432 — по правилу методички) и измеримая исходная точка: схема с инвариантами в уровне схемы, детерминированные данные, прогретый генератор с фиксированной конкурентностью. Инвариант «задача не может ссылаться на проект другого арендатора» доказан негативной проверкой (ошибка составного FK). Путь чтения подтверждён планом: Index Scan по частичному индексу без Sort, 50 строк, всё в кеше. Базовый замер: ~15.2 тыс. оп/с при workers=8, p95 0.66–1.05 мс, 0 ошибок; оценка «конкурентность/среднее» (8/0.521мс ≈ 15.4 тыс.) сходится с измерением. Вариант А (120 000 задач, 80/20): ~2.3 / ~13.9 / ~23.4 тыс. оп/с для workers=1/8/32, p95 ≈ 1.0 / 1.05 / 2.6 мс, p99 ≈ 1.1 / 1.12 / 3.1 мс, 0 ошибок во всех 12 прогонах; масштабирование 8 → 32 горутин даёт лишь ×1.7 при утроении времени ответа — ближайший к исчерпанию ресурс по совокупности данных (неизменный план, read=0, pool=workers) — процессор, а не диск и не пул соединений. Остановка по сроку и детектор гонок проверены.

**Ограничения (почему замер оптимистичен).** Локальный стенд с посторонней нагрузкой (~30 чужих контейнеров); замкнутый цикл генератора недооценивает хвост (следующий запрос не приходит, пока не завершился предыдущий); полностью прогретый кеш (`shared read=0`); «удобные» данные — короткие строки, идеальный частичный индекс, крошечный горячий набор из 50 строк; короткое окно (500 запросов, десятки миллисекунд) — статистика хвоста на 500 точках груба; локальный loopback-транспорт без сети. Утилизация CPU/iostat не логгировались — вывод об ограничивающем ресурсе опирается на план, буферы и форму кривой масштабирования, а не на прямой замер насыщения.

**Каких измерений не хватает для решения о шардинге.** Ни один ресурс не измерен исчерпанным — оснований для разделения данных по узлам нет. Чтобы получить право обсуждать шардинг, нужны: открытый поток независимых клиентов (не замкнутый цикл) при фиксированной целевой нагрузке; длительные окна наблюдения (часы) с мониторингом насыщения (утилизация CPU, iostat, pg_stat_statements, pg_stat_activity); смешанная нагрузка с записью; объёмы, при которых рабочий набор перестаёт умещаться в память (миллионы строк), и повторение на изолированном стенде без посторонней нагрузки. Только после измеренного исчерпания конкретного ресурса имеет смысл выбирать между оптимизацией запроса, индексом, кешем, репликой чтения, производным представлением и лишь затем — разделением по узлам.
